- 🔴 **이것은 윈도우 `.exe`가 아니다.** PyInstaller는 **크로스 빌드를 못 한다** — 맥에서 만들면 맥 실행 파일만 나온다. **수업용 윈도우 노트북에서 `pyinstaller build.spec`을 직접 돌려야** `.exe`가 나온다. 그때 **파이썬 3.11**을 쓴다(`build.spec` 주의사항, pasco 요구사항). 맥 빌드는 3.12로도 됐다.
- `collector/dist/`는 `.gitignore` 대상이라 GitHub에는 안 올라간다(17MB 바이너리를 git에 넣지 않는다). **iCloud 폴더라 기기 간 동기화는 된다.**

**윈도우 exe 만들기 — 절차 (2026-07-27 확정, 사용자가 윈도우 노트북에서 직접)**

PyInstaller는 크로스 빌드를 못 하므로 **윈도우에서 빌드해야 `.exe`가 나온다.** 단, 최종 `.exe`는 `9aaf027` 병합과 실제 센서 회귀가 끝난 소스에서 만든다. 어차피 윈도우 실물 확인이 개학 전 필수라 한자리에서 끝내는 것이 낫다(GitHub Actions 자동 빌드는 검토했으나 사용자가 직접 빌드를 택함).

1. **파이썬 3.11 설치** — python.org에서 3.11.x. 설치 화면 맨 아래 **"Add python.exe to PATH" 체크**(안 하면 `python`이 안 먹힌다). 3.12는 pasco 요구사항 밖이라 피한다.
2. **프로젝트 파일 옮기기** — iCloud Drive(윈도우용) 동기화가 가장 쉽다. `git clone`도 되지만 그 경우 **`collector/firebase-config.json`이 따라오지 않는다**(gitignore 대상). 없으면 손으로 만들어야 한다 — `firebase-config.example.json`을 복사해 `apiKey`·`projectId`를 채운다.
3. **명령 프롬프트에서**:
   ```
   cd collector
   pip install -r requirements.txt
   pip install pyinstaller
   pyinstaller build.spec
   ```
   → `collector\dist\과학데이터스튜디오_수집기.exe`
4. **확인** — exe를 두 번 눌러 → 브라우저에서 `http://127.0.0.1:5050` 열림 → 학급 코드 `TEST` 입력 → 학급 이름이 뜨면 성공. 이어서 온도 센서 연결까지 해 보면 윈도우 블루투스 경로까지 검증된다.

⚠️ **미리 알아 둘 것 — 윈도우가 exe 실행을 막을 수 있다.** 서명 없는 실행 파일이라 처음 실행 시 **"Windows의 PC 보호"** 파란 창이 뜬다. **[추가 정보] → [실행]**을 눌러야 열린다. 모둠 노트북 6대에서 학생이 각자 겪게 되므로, **수업 전에 교사가 한 번씩 눌러 두거나** 학생에게 미리 알려 줘야 한다. 백신이 삭제해 버리는 경우도 있어 개학 전 실제 확인이 필요하다.

**센서 번호 형식** (세션 F가 알아야 할 것) — 기기 이름은 `Temperature 117-880>18` 형태이고, `connect_by_id()`에 넘길 6자리 번호는 `117-880`이다. **뒤의 `>18`을 잘라내야 한다.** (`name.split()` 후 `">"` 앞부분만 취하면 됨. 이 처리를 빠뜨리면 번호 추출이 조용히 실패한다 — 세션 G도 처음에 이걸로 틀렸다.)

**부수 확인 사항**

- pasco가 보고하는 단위는 `'DegC'`이지만, `sensor.py`는 `PASCO_SENSORS`에 하드코딩한 `'℃'`를 쓰고 pasco 단위를 참조하지 않는다. **SPEC §5의 `unit` 규약을 지키는 올바른 처리다** — 고칠 필요 없음.
- pasco의 검색은 **기기 이름에 센서 종류 문자열이 포함되는지** 보는 단순 매칭이다(`'Temperature' in "Temperature 117-880>18"`). 세션 F의 `PASCO_SENSORS` 키가 이 매칭에 그대로 쓰이므로 키 이름을 임의로 바꾸면 검색이 깨진다.

### §12.2 설계 질문 — 실험마다 다른 고민을 담았다

| 실험 | d1 | d2 | d3 |
|---|---|---|---|
| 1 환기 | 무엇을 바꾸고 무엇을 같게 | 어떻게 잴까 | 어떤 결과면 환기가 필요한가 |
| 2 광합성 | 통제 항목이 화분·흙·잎 | **대조군은 왜 필요하고 몇 번 반복할까** | **어떤 차이면 '진짜 차이'인가** |
| 3 운동 | 사람마다 강도 기준 맞추기 | **언제 재야 공평한가 + 몸 안 좋은 친구** | (주제별로 다름) |
| 4 비열 | **같게 맞추기 어려운 것을 어떻게** | **센서 1대면 순서를 어떻게** | **재기 전에 예상 적기** |

굵은 글씨가 실험 1에 없는 질문이다. 형식만 흉내 낸 것이 아니라 **각 실험에서 실제로 막히는 지점**을 골랐다는 근거:

- **실험 4** — 주석에 판단 근거를 남겼다: "실험 1은 무엇을 바꿀지부터 정해야 하지만, 실험 4는 바꿀 것이 물질 하나로 이미 정해져 있다. 어려운 쪽은 반대로 **같게 맞춰야 할 것이 너무 많다는 것**이다." 그래서 d1을 "무엇을 같게 둘까"가 아니라 **"맞추기 어려운 것을 어떻게 맞출까"**라는 실행 계획 질문으로 세웠다. d3에서 **측정 전 예상을 적게** 하는 것도 이 실험만의 장치다 — 4단계가 "빨리 오른다 → 1℃ 올리는 데 열이 덜 든다"는 **관찰을 뒤집는 추론**을 요구하기 때문에 예상과 견줄 자리가 필요하다. "식용유가 더 빨리 오른다"는 답은 어디에도 흘리지 않았다.
- **실험 3** — 공통 d1·d2 + **주제별 d3**으로 절충했다("다섯 단계씩 두 벌을 만들면 학생이 지친다"). d2에 **"몸이 안 좋거나 심장이 약한 친구가 있다면 어떻게 할 건가요?"**를 넣은 것은 명세에 없던 판단이고, 사람을 재는 유일한 실험에서 꼭 필요한 질문이다. 힌트에 "이름이나 몸무게 같은 개인 정보는 적지 마세요"를 명시해 **절대 규칙 2·3**을 질문 안에서 지켰다.
- **실험 2** — d2·d3이 실험 1에 아예 없는 질문이다. d3은 3단계 "편차보다 뚜렷한가"의 복선으로, 판단 기준을 **측정 전에** 정해 두게 한다.
- 실험 2의 d1만 제목이 실험 1과 같다(`무엇을 바꾸고, 무엇을 똑같이 둘까`). 내용은 다르므로(화분·흙·잎) 문제 없다 — 변인 통제는 모든 실험의 공통 틀이라 오히려 같은 것이 낫다.
